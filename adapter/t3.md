# pstack on T3 Code

pstack was written for Cursor. This file says how to do each Cursor-specific thing in a T3 Code thread, on a
Claude Code thread or a Codex thread alike. **On the points below, this file overrides the skill you are
following**: subagents, models, schedules, pull requests, transcripts, UI proof, Cursor-only commands, and file
locations. Everything else in the skills applies as written.

T3 gives every thread the `t3-code` MCP tools. Hosts prefix their names (`mcp__t3-code__delegate_task`,
`mcp__t3_code__delegate_task`); this file uses the bare names. Outside T3 (no `t3-code` tools), skills that
dispatch subagents cannot run their panels: say so instead of improvising one.

## Subagents

poteto-mode's Subagents section applies through `delegate_task`:

- **The chat that receives `/poteto-mode` runs the playbook** and makes every `delegate_task` call. A child never runs the playbook.
- **A child gets only its brief.** Pass file pointers and absolute paths, never the parent's context.
- **`subagent_type: "poteto-agent"`** becomes a brief that opens with: "Read `~/.agents/skills/poteto-mode/SKILL.md` and `~/.agents/skills/poteto-mode/references/t3.md` in full before any work." `comment-sicko` becomes the same with `~/.agents/skills/poteto-mode/references/agents/comment-sicko.md`. Any other `subagent_type` needs no extra line.
- **`readonly: true`** becomes a sentence in the brief: inspect only, `git diff` is fine, change no file.
- **A writing child gets its own worktree** where the skill gives it one (Cursor's `.cursor/worktrees`, or `environment: "cloud"`). Create it first from `HEAD`: `git worktree add .claude/worktrees/<slug> -b <branch>`. Name it by absolute path in the brief as the only place the child writes, and tell it to run every command there and edit by absolute path. Record `git status --porcelain` before you dispatch and check it is unchanged after; then remove the worktree and branch.
- **`environment: "local"`** is the default: omit it.
- **Do delegated steps by delegating.** A step a skill says to delegate goes to `delegate_task`, not into your own tool calls, unless it is too small to brief; then say why.
- **End every reply that ran a playbook with a dispatch ledger**: one line per delegated step with its role and the `providerInstanceId/model` it ran on, or `in-thread: <reason>`.

## Available models

pstack uses many models on purpose: panels, second opinions, and cross-judges need different model families.
**Before the first dispatch in a session, call `orchestrator_capabilities`.** It lists every provider instance
T3 offers on this machine (for example `claudeAgent`, `claudeProxy`, `codex`, `codexProxy`, `grok`, `cursor`,
`opencode`, `pi`), each one's models, its option IDs and values (reasoning effort), its runtime modes, and the
model this thread inherits. It is the same live catalog as T3's model picker, custom models included.

- **Only dispatch to targets in that list.** The sheet says which target each role prefers; the catalog says
  what exists now. A provider can be disabled or signed out, and a model can be renamed.
- **A free choice comes from the catalog**: a skill that asks for "a different model", "a second opinion",
  "the strongest model", or N diverse runners picks targets from the catalog, preferring the sheet's entries,
  then other families the catalog offers, so the panel is as diverse as the machine allows.
- **The same model through two providers is still one family.** `claudeAgent` and `claudeProxy` both serve
  `claude-*`; a `claude` and a `gpt` reviewer are two families, two `claude` reviewers are one.
- **Say what ran.** The dispatch ledger names each child's `providerInstanceId/model`.

## The sheet

`~/.agents/t3-pstack-models.md` is the model choice per role for this machine, shared by Claude Code and Codex.
Read it before the first dispatch in a session. It replaces every model slug and every Models section in the
skills (`grok-4.7-xhigh-fast`, `claude-opus-5-5-xhigh`, and so on).

- **One line per role**, with the role names poteto-mode and setup-pstack use. A panel role (`arena runners`, `arena cross-judge pool`, `architect runners`, `interrogate reviewers`) holds a comma-separated list; one child runs per entry.
- **An entry** is `<providerInstanceId>/<modelId>` and optional `<optionId>=<value>` pairs, or `inherit-parent` (alias `auto`, which means: omit `target`). It maps 1:1 onto `delegate_task`'s `target`: `{ providerInstanceId, model, options }`. It splits at the first `/`.
- **Option IDs differ per provider.** Claude names its reasoning option `effort`; Codex and Grok name it `reasoningEffort`. Copy IDs and values from `orchestrator_capabilities`, never from another provider's line.
- **A model's family** is the first word of its model ID: `claude`, `gpt`, `grok`. Panels need at least two families. Your own family is the one `orchestrator_capabilities` reports as inherited.
- **A target T3 rejects** runs on another target of the same family from `orchestrator_capabilities`, and you say so. With none, the seat stays empty; a required second-family review with no reviewer is `BLOCKED: independent review`.
- **A role with no line** uses the `judgment and prose` line for judgment work and `feature, refactoring` for code.
- **Match the model to the job.** Start from the role's entry. The skills may ask you to raise or lower the
  reasoning level one step, or to pick a fast or a standard speed, for the job at hand. Do that within the
  catalog: change the entry's reasoning option to another value that provider lists, and for "fast" pick a faster
  model of the same family (for example `grok-4.7-build-fast`, `gpt-6-luna`, `claude-sonnet-5-5`) or the provider's
  speed option if it has one. Name what you chose in the dispatch ledger. Ignore the skills' `@<level>` syntax.
- **Cursor's own model names** (`composer-*`, `cursor-grok-*`, and slugs with an effort suffix such as
  `claude-opus-5-5-xhigh` or `grok-4.7-xhigh-fast`) are Cursor slugs. Read them as family and effort, then use the
  sheet's entry for that role.

### setup-pstack on T3

The sheet replaces Cursor's rule file. Steps 1–5 change like this; step 7 is unchanged.

1. Detect models with `orchestrator_capabilities` (provider instances, their models, and their option values).
2. Start from the current sheet, or from this machine's default sheet when there is none.
3. Ask for the budget as the skill says, then set each entry's reasoning option to the matching value
   (`unlimited` → `max`, `large` → `xhigh`, `medium` → `high`, `small` → `medium`) where the provider offers it,
   else its highest value at or below.
4. Validate every entry against `orchestrator_capabilities`.
5. Write `~/.agents/t3-pstack-models.md`: a `# budget: <label>` line, then one line per role. It applies to new
   threads on both harnesses.

## Pull requests

**Babysit** (poteto-mode's `playbooks/babysit.md`): the playbook's watcher is the `watch-pr` script in
`~/.agents/skills/poteto-mode/scripts/watch-pr/`. Loop it inside the turn (`watch-pr --pr <n> --timeout 540`,
with the shell timeout above 540 s and under the 600 s tool cap) in place of `/loop`. Use T3's
`watch_pull_request` only to wait for a human review: it wakes the thread on a failed check, passing required
checks, a new comment or review from another account, a conflict, or a close. `unwatch_pull_request` stops it.
Only a top-level thread can watch; a child that opens a PR returns its URL so the parent links and watches it.
T3 ignores comments from the GitHub account it reads with.

**Autopilot-full, autopilot-stack, orchestrate.** Starting one of these playbooks is the request for top-level
threads. Each PR owner (Cursor's "one cloud agent per PR") is a `t3_thread_launch` with
`workspaceStrategy: {type: "worktree", baseRef, branch, startFromOrigin: false}`, briefed with the playbook steps,
`t3.md`, and this thread's ID, so it reports back with `t3_thread_send`. Verifier lanes are `delegate_task`
children spread over the `interrogate reviewers` entries, so lanes span families. The hourly audit (`/loop 1h`)
is a `schedule_task` bound to this thread. Watch each owner's PR with `watch_pull_request`.

## UI proof

- **The project's verify skill first** (`.agents/skills/verify-*`), for every surface it covers.
- **Web apps**: `preview_open`, `preview_navigate`, `preview_snapshot` (refs expire on navigation), then `preview_click`, `preview_type`, and the other `preview_*` tools. Evidence is `preview_snapshot` with `save: true`, or `preview_recording_start` / `preview_recording_stop`, linked in the reply. Close tabs with `t3_preview_close`.
- **iOS Simulator / Android Emulator**: `device_list`, `device_open`, `device_screenshot`, `device_close`.

The evidence is the file these tools return, never your description of it.
